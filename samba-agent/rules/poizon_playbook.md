# 포이즌 주문 처리

SAMBA-WAVE(https://samba-wave.vercel.app/samba/orders)의 판매 주문을 MUSINSA·29CM·ABC마트(GRAND STAGE)·LOTTEON에서 소싱 구매하고, 원가·소싱주문번호를 SAMBA-WAVE에 기록·검증한다. 다른 소싱처는 절차가 추가되기 전까지 지원한다고 단정하지 않는다.

## 0. SAMBA Browser에서의 도구 규칙(다른 무엇보다 우선)
- 로그인은 `list_accounts` → `login`(키마스터). 아이디·비밀번호를 내가 타이핑하지 않는다.
- **결제 비밀번호·PIN은 절대 내가 누르거나 타이핑하지 않는다.** 결제 비밀번호 화면(무신사머니 NICE ePAY, 네이버페이·페이코·토스 보안 키패드)에 도달하면 `fill_secret`(itemType "password", provider: 무신사머니=site, 네이버페이=naver, 페이코=payco, 토스페이=toss, 카카오페이=kakao)를 부른다. 앱이 넣지 못하면 사람에게 넘어가므로 "결제 비밀번호를 직접 눌러 주세요"라고 알리고 기다린다. 키패드 화면에서 click/type/screenshot/ocr은 거부되며, 그것은 오류가 아니다.
- 캡차·추가 본인인증은 풀지 않는다. 그 단계만 사용자에게 넘긴다.
- **폰 결제 승인(토스페이·페이코 등 앱 승인)은 `phone_approve_payment` 한 번으로만 한다.** 이 도구가 담당 폰에서 **결제 앱이 올린 결제 요청 알림을 정확히 골라 누르고**(없으면 앱을 직접 열고), 앱 잠금 비밀번호와 결제 비밀번호를 키마스터 값으로 직접 누르고, 완료까지 확인한다. 결제할 카드가 정해져 있으면 `card` 에 카드 이름의 일부를 넘긴다 — **현대카드는 `card: '현대'`,KB(국민)카드는 `card: 'Smart'`, 롯데카드는 `card: 'LOCA',신한카드는 `card: '11번가',농협카드는 `card: 'zgm'`**(도구가 결제 앱 안에서 그 카드로 바꾼 뒤 결제한다. 목록에 없으면 `card-not-found` 로 멈추고 다른 카드로 결제하지 않는다). **내가 폰 도구(`phone_tap`·`phone_swipe`·`phone_key`)로 알림창을 내리거나 알림을 누르지 않는다** — 카카오톡의 '토스' 메시지 같은 엉뚱한 알림을 열게 된다. 카카오톡·문자·다른 앱도 열지 않는다. 도구가 실패하면 같은 도구를 **한 번만** 다시 부르고, 그래도 안 되면 폰을 더 만지지 말고 멈춰서 사유를 보고한다(결제창과 주문서는 그대로 둔다 — 사용자가 '결제만 다시'로 이어 간다).
- 사용자에게 비밀값(비밀번호·PIN·생년월일·카드번호)을 묻지 않고, 답변·메모·SAMBA-WAVE 어디에도 적지 않는다.
- 결제하기 직전 확인은 앱의 권한 모드에 맡긴다(자동이면 확인 없이 진행, guard면 앱이 묻는다). 내가 따로 "진행할까요?"를 묻지 않는다. 멈추는 경우는 아래 "멈추는 조건"뿐이다.
- 요소가 목록에 없으면 `find_elements`로 찾는다('255', '장바구니', '결제하기'). 옵션·드롭다운 항목은 role option/clickable로 나타난다. 팝업 결제창은 앱이 새 창/탭으로 열어 주므로 `list_tabs`로 찾아 `switch_tab`한다. 팝업이 안 보이면 결제하기를 반복 클릭하지 말고 탭 목록을 다시 본다.
- 입력은 클릭 → `type` → Enter/Tab으로 한다. DOM에 값을 주입하지 않는다.
- 진행 중 `progress`로 done/total을 알리고, 끝나면 `done`으로 보고한다.

## 1. 시작과 범위
- 사용자가 주문번호를 주면 마진 기준을 통과하는 한 결제·SAMBA-WAVE 기록·까대기까지 끝낸다.
- **멈추는 조건**: 마진 기준 미달, 품절·옵션 불일치, 캡차·추가 인증·결제 비밀번호 직접 입력처럼 사람 손이 필요한 단계, 규칙 없는 새 소싱처, 잔액 부족. 이때는 그 건을 보고하고 다음 건으로 간다.
- 무신사 프로필 탭에서 구매 버튼이 '회원 전용'이면(상단이 '로그아웃'이라도) 그 파티션의 로그인 토큰이 죽은 것이다. **로그아웃하지 말고** 바로 `navigate`로 https://www.musinsa.com/auth/login?referer=<상품URL> 에 간 뒤 `login` 도구 1회 → 상품 페이지로 돌아온다. '회원 전용'을 눌러 뜨는 팝업은 '확인'으로 닫는다. 이 절차는 한 번만, 그래도 안 되면 보고한다.
- **상품 페이지에서는 쿠폰을 아예 건드리지 않는다.** '쿠폰받기'·'사용 가능한 쿠폰'·'적용하기'·'첫 구매 쿠폰' 어느 것도 누르지 않는다(무신사의 쿠폰받기 버튼이 곧 그 팝업이다). 상품 페이지에서 할 일은 옵션(사이즈) 선택 → 구매하기 두 가지뿐이다. 쿠폰 발급·적용은 **주문서의 '쿠폰 사용' 시트**에서 한 번에 한다.
- **마진 미달 판정은 주문서의 실제 결제액으로만 한다.** 상품 페이지 표시가로 추정해 보류하지 않는다 — 쿠폰·적립금·선할인·결제수단 할인은 주문서에서만 반영된다(같은 상품이 표시가 152,100원 → 주문서 105,290원까지 내려간 실례). 주문서를 만들지 못했으면 '판정 불가'로 보고하고 막힌 지점을 적는다.
- 최신 사용자 지시가 이 절차보다 우선한다. 같은 대화에서 이미 받은 구매·계정전환 허가는 다시 묻지 않는다.
- 먼저 `list_tabs`로 열린 탭을 확인한다. 계정·결제창 상태가 이전 실행과 같다고 가정하지 않는다. 다른 세션이 같은 주문을 처리 중이면 손대지 않는다.
- **결제만 다시(열려 있는 주문서 재사용)**: `list_tabs` 에 이 주문의 소싱처 주문서 탭(무신사 `…/order/order-form` 등)이 이미 열려 있으면 **SAMBA 조회·상품 페이지·옵션 선택·주문서 생성을 다시 하지 않는다.** 그 탭으로 `switch_tab` 해서 상품명·옵션·수량·배송지·쿠폰·총 결제 금액이 그대로인지만 한 번 읽고 곧바로 결제 단계로 간다. 사용자가 '결제만 다시', '결제부터', '이어서 결제'라고 하면 반드시 이 길로 간다. 남아 있는 결제창(토스·페이코 팝업)은 요청이 만료됐을 수 있으니 '결제 취소하기'로 닫거나 `close_tab` 한 뒤 주문서의 결제하기를 **한 번** 다시 누른다. 주문서 내용이 달라졌거나 탭이 죽었을 때만 주문서를 새로 만든다.

## 2. 대상 선정(SAMBA-WAVE)
- **주문 검색의 기간은 처음부터 '올해'(또는 전체)로 놓고 조회한다.** 기본값 '오늘'로 먼저 찔러 보고 0건이면 넓히는 짓을 하지 않는다 — 매번 한 번 더 조회하는 낭비였다(실기). 주문번호로 찾을 때도 같다.
- 주문 URL: https://samba-wave.vercel.app/samba/orders. `login`으로 로그인(/samba/login).
- 조건: **주문상태 드롭다운 = 주문접수**, 모든 페이지를 확인하고 최신순으로 한 건씩 처리한다. 별도 요청이 없으면 건수 제한을 두지 않는다.
- 주문번호 옆 배송상태 표시와 주문상태 드롭다운은 다른 값이다. "배송대기중" 표시만으로 구매됐다고 단정하지 않는다. **SAMBA-WAVE 행의 소싱주문번호가 비어 있으면 소싱처 주문내역(무신사 마이페이지 등)을 뒤지지 않는다** — 중복 확인은 소싱주문번호가 있거나 간단메모에 결제 흔적이 있을 때만 한다(실기: 두 계정 주문내역 확인에 100초 낭비).
- 제외: 소싱주문번호 있음, 구매완료, 취소/반품/교환, 가격X/재고X, 구매보류, 다른 작업자 처리중. 결제됐는데 기록만 빠진 건은 기록 보완이 우선이다.
- 원문링크의 상품과 판매 주문의 품번·색상·옵션·수량을 대조한다. 상품주문번호와 판매처 주문번호를 구분한다. 명칭 번역이 달라도 품번·정확한 옵션으로 맞추고, 불명확하면 보류한다. 원문링크는 새 탭으로 열릴 수 있으니 클릭 뒤 `list_tabs`로 대상 탭을 확인한다.
- 행 번호나 첫 행을 주문 식별자로 쓰지 않는다. 새로고침·필터 변경 뒤 첫 행이 바뀔 수 있으니 항상 주문번호·상품·옵션을 대조한다.
- '간단메모'는 운영 메모, '고객메모'는 고객/배송 정보다. 원가 0일 때 보이는 큰 수익은 실제가 아니다.
- **poison 외 마켓(KT알파쇼핑·롯데홈쇼핑·쿠팡 등)은 소싱처 정가와 고객 결제액을 비교해 배송 방식을 정한다.** 고객이 받은 물건의 정가가 본인 결제액보다 싸면 클레임이 나므로 사무실을 거친다. **소싱처 정가 < 고객 결제액 → 까대기**(경주 사무실, SAMBA 배송비 2,300원). **소싱처 정가 > 고객 결제액 → 직배**(고객 주소로 직접 발송, SAMBA 배송비 비움). 비교 기준은 세일가가 아니라 **정가** — 세일 중이면 상품 페이지에 취소선으로 표시된 정상가를 읽는다. 사용자가 배송 방식을 직접 지시했으면 그 지시가 먼저다.
- **SAMBA 검색칸을 선택자로 잡을 때 `input[type="text"]` 를 쓰지 않는다.** 상단 검색칸에는 type 속성이 없어 걸리지 않고, 주문 행의 '쿠팡노출상품명' 칸이 먼저 잡혀 남의 주문 데이터를 덮어쓴다. 검색 유형 select(옵션 '주문번호') 바로 뒤의 input 이 검색칸이다. 입력 직후 값이 어느 칸에 들어갔는지 확인한다. 행 안의 칸은 placeholder 로 구분한다: `소싱주문번호`, `실구매가 (식 가능: …)`, `배송비 (식 가능)`, `송장번호`, `간단메모`, `쿠팡노출상품명`.
- 행 위쪽의 `직배주문`/`까대기주문`은 표시용이다. 누를 것은 금액 아래 플래그 줄의 `직배`/`까대기`/`선물` — 글자가 정확히 일치하는 버튼을 누른다(포함 검색으로 첫 버튼을 잡지 않는다).
- '주문 가져오기/송장수집 자동실행'이 켜져 있다는 것은 구매 자동화가 돌고 있다는 뜻이 아니다.

## 3. 까대기와 사무실 배송
- **poison 판매건은 소싱처와 관계없이 전부 까대기**(사무실 수령). ABC마트는 poison 외 마켓 건도 까대기다. 구매와 SAMBA-WAVE 저장을 마친 뒤 금액 아래 플래그 줄의 **까대기 버튼**을 누른다(저장되면 주황색, action_tag=kkadaegi).
- 사무실 주소는 **경북 가상시 사무실길 58**. 이 주소의 기존 기본 배송지는 수령인·연락처·층·호수 표기가 달라도 추가·수정하지 않는다. 포이즌 창고 주소와 혼동하지 말고 창고로 직송하지 않는다.
- 사무실 주소가 등록돼 있지 않을 때만 새 배송지로 **김사무 / 010-0000-0000 / 99999 / 경북 가상시 사무실길 58, 1층 102호**를 쓴다. 기본 배송지를 임의로 바꾸지 않는다.
- **직배(고객 주소로 직접 발송)의 배송지 입력 — 기본배송지는 건드리지 않고, 그 바로 아래 한 칸만 쓴다.** 무신사 주문서 → `배송지 변경`(별도 창, `list_tabs` 로 찾아 `switch_tab`). 목록은 위에서부터 [기본 배송지 · 수정] → [둘째 항목 · 수정 · 삭제] → [셋째 항목…] 순서다. **누를 것은 목록에서 두 번째로 나오는 `수정` 버튼**(기본 배송지의 `수정` 바로 다음 것, 둘째 항목에 '최근 사용' 표시가 붙어 있어도 같다)이다. 그 항목을 이번 고객 정보로 덮어써 저장 → 목록에서 그 둘째 항목을 선택 → `변경하기`.
  - **목록 아래쪽에 같은 고객 이름의 배송지가 이미 있어도 그것을 고르거나 수정하지 않는다.** `배송지 추가하기`도 누르지 않는다 — 직배는 언제나 둘째 항목 하나를 덮어써서 쓴다(목록이 늘어나지 않게). 둘째 항목이 아예 없을 때(목록에 기본 배송지뿐일 때)만 `배송지 추가하기`로 하나 만든다.
  - 덮어쓰기 전에 둘째 항목의 수정 화면에서 **휴대폰번호 칸의 기존 값이 채워져 있는지** 본다. 채워져 있으면 그대로 두고, 비어 있을 때만 `fill_secret(identity.phone)` 으로 채운다.
  - 바꾸는 것은 **이름·우편번호·주소·상세주소** 네 가지다. **휴대폰번호는 그 슬롯에 있던 값(사용자 본인 번호)을 그대로 둔다.** 새 배송지를 추가하는 경우에만 `fill_secret(itemType 'identity', field 'identity.phone', format 'digits')` 로 사용자의 CS 연락처를 넣는다(키마스터 전역 신원정보). not found 면 다른 번호를 가져다 쓰거나 추측하지 말고 멈춰서 알린다.
  - **고객 번호(안심번호 0504-… 포함)는 주문서 어디에도 적지 않는다** — 연락처 칸에도, 배송 요청사항에도(택배·소싱처 연락은 사용자가 받아 고객에게 안내한다). **배송 요청사항 칸은 아예 건드리지 않는다** — 열지도, 고르지도, 입력하지도, 확인하려고 눌러 보지도 않는다. 주문서에 이미 들어 있는 값 그대로 결제한다(SAMBA 고객메모에 배송 요청이 있어도 옮기지 않는다).
  - 주소 찾기: 검색창은 이중 iframe 안에 있다. `시/구 + 도로명 + 건물번호`로 검색해 도로명 결과를 고르고 SAMBA 의 지번주소·우편번호와 대조한다. 상세주소는 SAMBA 둘째 주소줄의 동/호 그대로. 포커스가 이름 칸 같은 곳으로 새면 글자가 엉뚱한 칸에 들어가므로, 입력 뒤 어느 칸에 들어갔는지 확인하고 잘못 들어간 값은 바로 지운다.
  - `기본 배송지로 설정`은 체크하지 않는다. 창이 닫힌 뒤 주문서의 배송지가 고객 주소로 바뀌었는지 **결제 전에** 화면으로 다시 확인한다.

## 4. 재고 판정
- **재고X는 정확한 요청 옵션에 품절·판매종료가 명시된 경우만.** 다른 옵션·추천상품 품절은 근거가 아니다.
- 가격·구매 패널·선택 버튼이 안 보이거나 목록에 빠진 것은 품절이 아니다. `find_elements`, 스크롤, `screenshot`, 새로고침으로 실제 구매 패널과 색상/사이즈 목록을 확인한다.
- 확인 불가는 '재고 확인 불가'로 보류한다. 재고X 저장 직전에 근거를 다시 확인한다.

## 5. 계정·혜택 비교
- **빠르게 하는 법(필수)**: 계정마다 프로필 탭을 따로 쓴다 — `new_tab({ url, profile: 'buyer02' })`, `new_tab({ url, profile: 'buyer01' })`(29CM도 계정 ID 를 프로필 이름으로). 프로필은 쿠키가 분리돼 **로그아웃·재로그인 없이** 여러 계정이 동시에 로그인 상태로 남는다. 각 탭에서 `login`(프로필 이름과 같은 계정을 고른다)은 처음 한 번만 필요하고 다음 실행부터는 이미 로그인돼 있다. 두 탭 모두 같은 옵션으로 주문서까지 만든 뒤 `run_js` 한 번으로 `tabs.switch` 하며 금액을 읽어 비교한다. 비교용 탭은 닫지 말고 남겨 다음 주문에 재사용한다.
- **무신사는 buyer01(성희) 한 계정으로 주문서를 만들고 결제한다.** 결제 할인(즉시할인·카드)은 이 계정만 가능하므로 비교 주문서를 따로 만들지 않는다. buyer02(병기)는 buyer01 이 결제 불가(잔액 부족·핵심 쿠폰 없음)일 때만 무신사머니로 대체한다. 29CM는 아래 6계정. 현재 로그인 계정이나 SAMBA-WAVE의 미리 선택된 계정만 보고 구매하지 않는다.
- 동일 품번·색상·옵션·수량·배송 조건의 **실제 주문서**를 계정별로 만든다. 최대 쿠폰, 회원등급 할인, 기존 적립금 사용, 선할인, 후기 제외 신규 적립, 실제 배송비, 결제수단별 최종 원가를 기록한다. 상품 페이지 예상가로 대체하지 않는다. 비교 주문서를 못 만들면 비교 불가로 보류한다.
- 로그인·주문서는 확인했지만 잔액 부족·머니 계좌 미등록 등 결제 불가 계정은 "비교 완료/결제 불가"로 구분한다. 충전·가입·계좌 등록을 전제로 최저가라고 하지 않는다.
- 동률은 현재 로그인 계정 우선. 계정전환 뒤 최종 계정·상품·옵션·수량·혜택·배송지를 다시 확인한다. 비교 중에는 결제하지 않는다.

## 6. 원가와 구매 판단
- 기본 원가 = 실제 결제액 − 후기 제외 신규 구매/결제 적립금 + 사용한 기존 적립금 + 결제액에 포함되지 않은 실제 배송비.
- 주문서 오른쪽 '적립 혜택' 표의 '후기 적립'·'무신사머니 결제 적립' 같은 항목은 **링크를 누르지 않는다**. 표시된 금액만 읽어 원가에 쓴다(누르면 화면만 바뀌고 도구 호출만 낭비된다).
- 선할인은 결제액에 이미 반영됐으므로 다시 빼지 않고, 기존 적립금 사용액에 섞어 더하지도 않는다. 기존 포인트 사용액은 원가에 다시 더한다. 후기 적립·부가세 환급·패널티 회피는 넣지 않는다. 포이즌 재발송비는 0원.
- 카드 할인은 사용자 확인 할인율을 실제 카드 결제분에 적용한다. 이미 청구액에 포함된 할인은 다시 빼지 않는다.
- **마진율 = (SAMBA 정산금 − 최종 원가) ÷ SAMBA 매출 × 100.** 판매마켓이 **poison**이면 **−3% 이상** 이행. **poison 외 마켓(롯데홈쇼핑·쿠팡 등)은 0% 미만이면 구매하지 않는다.** 반올림 전 값으로 비교하고 입력 금액은 원 단위 반올림.
- 허용 비교 수단(buyer01): **무신사페이(등록 카드: 농협카드 등 이 계정에 실제 등록된 카드)**, 무신사머니, 토스페이·페이코·카카오페이, 현대·삼성·롯데카드. 즉시할인 카드 가운데 이 수단들에 해당하는 것을 할인 큰 순서로 시도한다. **결제창이 가입·휴대폰 번호·생년월일·본인인증을 새로 요구하면 그 계정에 그 수단이 없는 것이다 — 입력하지 말고 창을 닫고 다음 카드로 넘어간다.** 계정에 없는 카드를 새로 등록하지 않는다.
- **무신사 buyer02(병기) 계정은 무신사머니 결제만 허용한다.** 이 계정 주문서에서는 토스·카카오·페이코·카드 비교를 하지 않고 무신사머니 금액만 읽는다(즉시할인 카드도 대상 아님). buyer01(성희)은 위 허용 비교 수단 그대로.
- 자동구매 범위: 아래 허용 수단 가운데 **원가가 가장 낮은 수단**으로 결제한다(카드 청구할인·적립 반영). 원가가 같으면 무신사머니. 허용 수단이 아닌 것이 더 싸면 차이만 기록하고 허용 수단 중 최저로 결제한다.
- 최선 조건도 마진 기준 미달이면 구매하지 않고, SAMBA-WAVE 그 주문 행의 **가격X 버튼을 눌러 체크**한 뒤 간단메모에 `관리자 금액확인필요`를 남긴다. 계산 근거는 보고로만 전달한다.
- **마진 미달 건은 가격X를 누른다**(주문서의 실제 결제액으로 판정한 경우에만 — 판정 불가·주문서 미생성은 가격X 아님). 가격X는 한 번만 누르고 버튼 색이 바뀐 것으로 확인한다(다시 누르면 해제된다). 인증 문제·대체 결제수단 승인 대기는 가격X/재고X가 아니다.
- 사용자가 **별도 샘플 추가 구매를 명시한 경우에만** 이미 산 상품을 추가 구매한다. 기존 소싱주문번호/원가에 덮어쓰지 않는다.

## 7. 무신사(MUSINSA)
- 상품: 원문링크의 품번·색상·사이즈·수량을 대조. 고정 구매 패널이 따로 있을 수 있다(과거 `.FixedArea__Container-…`; 바뀌었으면 현재 화면에서 구매하기·옵션 영역을 다시 찾는다). 색상·사이즈를 직접 펼쳐 해당 옵션 재고를 확인한다. 옵션 항목은 `find_elements`로 '255'·'BLACK'처럼 찾아 누른다.
- 구매하기를 누르면 **사은품 안내 모달**이 뜨는 상품이 있다 — 모달의 `바로 구매하기`를 한 번 더 눌러야 주문서로 넘어간다. 반응이 없다고 구매하기를 반복해 누르지 말고 화면을 다시 읽어 모달 여부를 본다. 같은 자리를 되풀이해 누르면 추천상품의 구매 버튼이 눌려 엉뚱한 주문서가 생길 수 있으니, **주문서의 상품명·옵션·금액을 결제 전에 반드시 대조한다.**
- **적립금 사용 제한 상품**이 있다. 주문서의 '보유 적립금 사용' 한도가 0원이고 구매 적립/선할인 라디오가 비활성이다. 이때는 잔액이 많아도 사용 0원이 정상이고, 원가에 더할 '사용한 기존 적립금'도 0이다(저장 실패로 오인하지 않는다).
- 주문서 원가: 최대 쿠폰·등급할인 적용. **보유 적립금 50,000원 이상이면 주문 허용 최대액 사용, 미만이면 0원**(사용자 별도 지시 우선, 29CM에는 적용 안 함). 구매 적립/선할인 중 선택 가능하면 **선할인 우선**. 적립금 사용을 바꾼 뒤 쿠폰·선할인·적립·최종액을 다시 읽는다. 주문서 요약의 적립금 사용액에는 기존 적립금과 선할인이 합산될 수 있다 — 원가에 다시 더할 것은 **소비한 기존 적립금만**. 선할인 후에도 남는 무신사머니 기본/프로모션 적립은 실제 표시 금액으로 반영(후기 적립 제외).
- **카드 청구할인(무신사에도 적용)**: 현대카드로 결제되면 카드 결제액의 **2.7%**, 롯데카드·**KB국민카드**로 결제되면 **2%**가 카드 대금 결제 때 할인된다. 즉시할인이 아니라서 주문서·결제창에는 보이지 않는다 — 원가 계산에서 직접 반영한다: **현대카드 원가 = 카드 결제액 × 0.973 − 적립**, **롯데카드·KB국민카드 원가 = 카드 결제액 × 0.98 − 적립**. buyer01 에서 현대카드는 PAYCO, 롯데카드는 토스페이로 결제한다. 즉시할인과 청구할인은 함께 받는다(즉시할인이 반영된 결제액에 청구할인율을 곱한다). KB국민카드는 이 계정에 등록된 결제 경로(무신사페이 등록 카드·간편결제)로 결제될 때 적용한다. 그 밖의 카드(농협 등)·무신사머니에는 청구할인이 없다.
- 배송: 사무실길 58 사무실 배송지 유지.
- **결제수단 비교(buyer01)는 주문서 위쪽 '즉시 할인 N개' 카드를 눌러서 한다.** 아래 '결제 수단' 라디오(토스페이·카카오페이·페이코…)를 누르는 것으로는 할인이 반영되지 않는다. 카드를 누르면 결제수단+카드 조합이 선택되고 총 결제 금액에 즉시할인이 반영되므로, 허용 수단의 카드를 하나씩 눌러 총 결제 금액을 읽는다. 카드를 누른 뒤에도 원가는 '총 결제 금액'으로 읽는다. buyer02 는 무신사머니 라디오만.
- 주문서의 '즉시 할인' 목록은 보유 혜택이지 적용 가능액이 아니다. `전체보기`를 열면 **최소 결제금액 조건과 비활성(회색) 여부**가 보인다(예: 토스페이×삼성카드 1만원 할인은 15만원 이상). 조건을 확인하지 않고 '더 싼 수단이 있다'고 보고하지 않는다. 토스페이×계좌, 카카오페이×페이머니처럼 **지정 카드가 아닌 조합은 허용 수단이 아니다** — 차이만 기록한다.
- **비교와 결제를 나눈다.** ① 비교: 허용 수단의 즉시할인 카드를 하나씩 눌러 '총 결제 금액'만 읽는다 — **이 단계에서는 '결제하기'를 절대 누르지 않는다**(누를 때마다 결제창이 뜬다). 카드를 누른 뒤 아래 '결제 수단' 영역에 그 카드가 **'등록하기'·'발급하기' 버튼과 함께** 보이면 이 계정에 등록되지 않은 카드다 — 비교 대상에서 빼고(등록·발급하지 않는다) 다음 카드로 간다. 등록된 카드만 후보다. ② 선택: 수단마다 **원가**(총 결제 금액에 카드 청구할인 — 현대 ×0.973 · 롯데 ×0.98 · KB국민 ×0.98 — 과 적립을 반영한 값)를 계산해 가장 낮은 수단을 고르되, **무신사머니 원가보다 싸야** 한다(아니면 무신사머니). 즉시할인 카드가 없어도 PAYCO(현대카드)·토스페이(롯데카드)는 청구할인만으로 후보가 된다 — 이때는 아래 '결제 수단' 라디오에서 고른다. 보고에 수단별 결제액·원가를 함께 적는다. ③ 결제: 고른 수단의 카드를 다시 누른 뒤 **'결제하기'를 한 번만** 누른다. 결제창에서 그 계정에 해당 카드·계좌가 없는 것이 확인되면(카드 목록에 없음·가입 요구) 창을 닫고 다음으로 싼 수단으로 ③을 다시 한다. 시도한 수단과 금액을 기록한다.
- **결제가 끝나면 다른 어떤 확인보다 먼저** 소싱처 주문번호를 읽어 SAMBA-WAVE 에 소싱주문번호부터 저장한다. 그다음 주문계정·실구매가·메모·까대기 순으로 채운다 — 중간에 끊겨도 소싱주문번호만 있으면 이중 구매가 막힌다.
- **결제창 금액이 주문서 '총 결제 금액'과 다르면 바로 포기하지 않는다.** 결제창을 다시 읽어 할인 줄을 확인하고, 그래도 다르면 창을 닫고 같은 수단으로 **한 번 더** 시도한다. 두 번째도 다를 때만 다음으로 싼 수단으로 넘어가고, 그 사유와 두 금액을 최종 보고와 간단메모에 남긴다(실기: 농협 즉시할인이 정상인데 한 번 보고 물러났다).
- **buyer01 외 계정(buyer02 등)은 쿠폰에서 더 유리하지 않으면 주문서를 더 만들거나 추적하지 않는다.** 결제 할인(즉시할인·카드)은 buyer01 에서만 가능하므로, 다른 계정은 쿠폰 적용가가 buyer01 보다 확실히 낮을 때만 후보로 남긴다.
- 결제 흐름: 주문서 결제하기 → `money.musinsapayments.com` 창의 금액 확인 → 그 창의 결제하기 → NICE ePAY(`m.niceepay.com/epay/pinCert.do`, 별도 창) 결제 비밀번호. 매 단계 계정·대상·금액을 확인한다. **키패드는 수십 초 안에 만료된다** — 비밀번호 화면이 보이면 스냅샷·화면 캡처·대기를 끼우지 말고 곧바로 `fill_secret`(password, provider site)을 부른다(앱이 배치를 읽어 6자리를 연속으로 누른다). `시간 초과로 인한 오류`가 나면 결제창부터 다시 연다. 내가 숫자를 누르지 않는다.
- 무신사페이 결제창(등록 카드 결제, 6자리 키패드)의 결제 비밀번호는 무신사머니와 같다 — `fill_secret`(password, provider site)를 **한 번만** 부른다. 같은 결제창에서 다시 부르지 않는다(오답 5회면 잠긴다). 오답 안내가 보이면 즉시 멈추고 사용자에게 넘긴다.
- 잔액 부족은 충전·상품권 등록으로 해결하지 않는다(별도 승인 범위). 머니 인출은 하지 않는다.
- 완료 후 무신사 주문 상세에서 결제상태·주문번호·품목·옵션·수량·주소·금액 확인. 성공하면 주소가 `www.musinsa.com/order/result/{주문번호}` 꼴이고 그 번호가 SAMBA 에 넣을 소싱주문번호다. 주문번호를 시각·추정으로 만들어 내지 않는다.

## 11. 결제 직전과 완료
1. **결제 직전에 SAMBA-WAVE를 다시 조회하지 않는다.** 처음 조회에서 읽은 행 정보(상태·소싱주문번호 빈칸·수익률 자료)를 그대로 쓴다. SAMBA-WAVE 탭은 결제가 끝난 뒤 기록할 때 다시 연다.
2. 최종 소싱 로그인 계정, 품번/색상/옵션/수량, 쿠폰·적립·결제액, 사무실 주소, 결제수단을 검증한다. 수량 추가·추천상품·부가서비스를 붙이지 않는다.
3. 결제 팝업의 금액·수단도 확인한다. 계정전환·배송지 변경으로 품목이 바뀌면 멈추고 정확한 단품 주문서를 다시 만든다.
4. 결제를 누가 실행했는지(사용자/에이전트) 구분한다. '주문이 존재함'과 '내가 결제함'은 다르다.
5. 팝업 종료·잔액 감소만으로 성공을 보고하지 않는다. 소싱처 주문 완료/상세에서 결제상태·주문번호·상품·옵션·수량·배송지·금액을 검증한다. 불명확하면 주문내역을 먼저 확인하고 재결제하지 않는다.
6. 무신사머니 잔액은 결제 가능 여부 판단에 필요한 만큼만 확인한다. 총잔액·일반 머니·상품권 충전금은 다른 값이다. 무신사와 29CM는 같은 통합계정의 지갑을 공유할 수 있으니 두 번 합산하지 않는다. 자동 충전 조건이 붙는 결제는 진행하지 않는다.

## 12. SAMBA-WAVE 저장 순서와 검증
1. 정확한 판매 상품주문번호 행에서 **실제 소싱처 구매계정** 선택 → 저장 확인. 29CM 결제를 같은 이름의 MUSINSA 계정에 저장하지 않는다.
2. **소싱처 주문번호**를 화면 표시값 그대로 입력하고 입력 종료(29CM는 ORD 형식, URL 내부 숫자 ID 아님). 상태가 배송대기중으로 바뀌어도 단독 결제 증거로 쓰지 않는다.
3. **배송비·간단메모**를 한 필드씩 저장. 배송비는 판매처·배송 방식 기준: **poison 건은 비움 / poison 아닌 마켓의 까대기 건은 2,300원 / 같은 마켓이라도 직배 건은 비움**(사무실 경유가 없어 재발송비가 없다). 기존 유용한 메모는 보존.
4. **실구매가**에 최종 원가를 숫자로 넣고 Enter/Tab으로 확정. 각 저장 결과를 확인한 뒤 진행하며 원가는 마지막에 저장.
5. 배송 방식 플래그를 **반드시, 하나만** 누른다 — 이 단계를 빼먹으면 기록이 끝난 것이 아니다. 고객 주소로 직접 발송한 건(사용자가 직배로 지시한 건 포함)은 **직배**, 사무실 수령은 **까대기**. 까대기는 주황(rgb(217,119,6)), 직배는 파랑(rgb(37,99,235))으로 바뀌면 저장된 것이다. 누른 뒤 그 버튼의 색을 다시 읽어 바뀌었는지 확인하고, 안 바뀌었으면 한 번 더 누른다. 둘 다 누르지 않는다. 미발급 송장번호를 만들거나 마켓으로 전송하지 않는다.
6. 새로고침 후 같은 상품주문번호를 재검색해 계정·소싱주문번호·실구매가·배송비·메모·상태·**배송 방식 플래그 색**이 유지되는지 확인한다. 누락 필드만 보완. 플래그가 안 켜져 있으면 완료로 보고하지 말고 5를 다시 한다.
- 저장 함정: 각 필드는 독립 요청이다(메모 저장 성공이 원가 저장을 보증하지 않음). 로컬 수익률 변화나 입력칸 값만 보고 영속성을 단정하지 않는다. 사용자가 직접 수정했다고 하면 먼저 새로 조회하고 덮어쓰지 않는다.
- **빈 값은 화면에서 저장되지 않는다.** 칸을 비우고 빠져나와도 서버 값은 그대로 남는다. 잘못 들어간 값을 지워야 하면 임의로 다른 값으로 덮지 말고, 어느 주문의 어느 칸인지 사용자에게 알린다(서버 API 를 직접 부르지 않는다).
- 반영이 늦다는 이유만으로 저장 실패를 단정하지 않는다 — 재검색해 최신 값을 본다. 수식 입력(예: 30000*.973+2300)은 지원되지만, 다시 넣을 때는 최종 숫자로 넣는다. 실구매가에는 원가를, 실제 승인액·할인·적립의 근거는 메모·보고에 구분해 적는다.
- 간단메모 규칙: 구매 못한 건(마진 미달·가격 이상·보류)은 `관리자 금액확인필요`만(마진 미달은 가격X 체크도 함께). 구매 완료 건은 구매계정·결제수단·실결제액·원가 한두 줄. 비밀값·계좌번호 금지.

## 13. 회복
- 탭이 응답하지 않으면 같은 탭에서 재시도하지 말고 불필요한 탭을 닫고 대상 페이지를 새 탭으로 다시 연다. 세션이 풀렸을 수 있으니 로그인 상태부터 확인.
- 한 상품을 여러 탭으로 겹쳐 열어 두지 않는다. 끝난 결제창·주문완료·중복 상품 탭은 닫고, 느린 탭은 `switch_tab` 으로 앞으로 가져온 뒤 다시 읽는다(사용자에게 탭을 띄워 달라고 하지 않는다).
- 로그인 버튼을 글자로 찾을 때 '네이버 아이디로 로그인' 같은 소셜 버튼을 누르지 않게 정확한 요소를 고른다.
- 로그인 자동 채움이 안 되면 아이디 칸을 클릭해 포커스 후 `login` 재시도, 그래도 안 되면 새 탭에서 로그인 페이지를 다시 연다.
- 네이버 계정 전환 중 캡차가 뜨면 풀지 않고 사용자에게 넘긴다.
- 결제창 '결제진행중' 상태로 멈춘 주문서는 결제되지 않은 것이다. 새 주문서를 만들어 처음부터 진행한다.
